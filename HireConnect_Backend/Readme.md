HIREFLOW - BACKEND DESIGN DOCUMENT1. Project OverviewHireFlow is a comprehensive job recruitment platform designed to connect job seekers with employers. The platform supports three primary user roles: JOB_SEEKER (can search and apply for jobs), EMPLOYER (can create companies, post jobs, and manage applications), and ADMIN (can manage all users, companies, and platform settings). This document serves as the complete technical blueprint for the backend implementation.2. Technology StackLanguage: JavaFramework: Spring BootWeb Layer: Spring MVC, Spring REST APIData Access Layer: Spring Data JPA, HibernateDatabase: PostgreSQLSecurity: Spring Security, JWT (JSON Web Tokens), BCrypt Password HashingValidation: Jakarta Bean Validation (Hibernate Validator)3. Backend ArchitectureThe backend follows a standard multi-tier architectural pattern:Controller Layer: Intercepts incoming HTTP requests, maps them to appropriate services, and returns HTTP responses using DTOs.Service Layer: Contains the core business logic, enforces authorization rules, and acts as a bridge between controllers and repositories.Repository Layer: Interfaces with the database via Spring Data JPA.Database Layer: PostgreSQL relational database holding all persistent application data.Key Architectural Rule:Data Transfer Objects (DTOs) act as the strict boundary between the web layer and the service layer. JPA entities are isolated to the service and repository layers and are never returned directly by REST controllers.4. Package StructureThe logical package structure follows domain and technical separation:config - Security, CORS, and Application configurationscontroller - REST API endpointsdto - Request and Response Data Transfer Objectsentity - JPA Entitiesenums - Enumerationsexception - Custom exceptions and global exception handlerrepository - Spring Data JPA interfacessecurity - JWT filters, UserDetails implementationservice - Business logic interfaces and implementations5. Security DesignThe backend uses stateless authentication secured via Spring Security and JWT. BCrypt is utilized to securely hash passwords before database storage.Complete Authentication Flow:Register Request -> Validate Email uniqueness -> Hash password with BCrypt -> Save to Database -> Login Request -> Verify credentials -> Generate JWT -> Frontend stores token -> Frontend sends Authorization: Bearer <token> on protected routes -> OncePerRequestFilter intercepts -> Validates JWT -> Extracts email/role -> Loads UserDetails -> Sets SecurityContext -> Execution passes to Controller -> Service layer executes RBAC & Ownership authorization checks -> Response returned.21. JWT DesignPayload structure: subject (email), role, iat (issued at time), exp (expiration time).Token Generation: Signed using HMAC512 with a secret application key.Expiration: Set to expire after 24 hours. If a token expires, the backend rejects it.Invalid/Missing/Malformed Token: The OncePerRequestFilter catches this and allows Spring Security to throw an AuthenticationException, resulting in a 401 Unauthorized response before hitting any controller.22. Ownership/Authorization RulesRole authorization (RBAC) handles what a user can do, but Ownership rules dictate which records they can do it to.Company Ownership: An EMPLOYER can only update/delete the company linked to their id.Job Ownership: An EMPLOYER can only update/delete jobs linked to their specific companyId.Application Ownership: A JOB_SEEKER can only view/delete applications tied to their applicantId. An EMPLOYER can only view/update applications for jobs tied to their companyId.Implementation: The Service layer fetches the authenticated user from the SecurityContext and strictly compares their ID against the createdBy or employerId fields in the target database records. If they don't match, an AccessDeniedException (403) is thrown.24. Validation RulesDTO fields enforce constraints conceptually:User name/email/password: @NotBlank. Email must follow standard format (@Email). Password minimum 8 characters (@Size(min=8)).Company name: Required (@NotBlank).Job title/description: Required (@NotBlank).Salary: Must be >= 0 (@PositiveOrZero).Salary maximum: Must be logically >= salary minimum (custom class-level validation).Application resume: URL must be provided (@NotBlank).Application status update: Target status must be valid and cannot be null (@NotNull).25. Business RulesEmail must be globally unique across all roles.Passwords must be hashed; raw passwords never exist in DB.Public registration endpoints cannot create ADMIN users.Disabled users (enabled = false) cannot successfully log in.An Employer can have only one Company record.Employers can modify only their own company profile.Employers can modify only their own job postings.Public users and Job Seekers can view only ACTIVE jobs.Job Seekers can apply only to ACTIVE jobs.Job Seekers cannot apply after a job's application deadline has passed.Job Seekers cannot apply twice to the exact same job.Employers cannot apply for jobs (prevents data logic errors).Job Seekers can access only their own application history.Employers can access applications only belonging to their own posted jobs.Employers can update application status only for their own jobs.Only an ADMIN can view the global dashboard, manage users, or globally delete resources.Users cannot change their own role after registration.Users cannot toggle their own enabled status (only Admin can ban/unban).CLOSED jobs cannot receive new applications.26. Frontend Integration PlanThe API contract is designed so the future frontend communicates exclusively via HTTP/JSON at the /api base URL.Login Handling: Frontend calls /api/auth/login. On 200 OK, frontend extracts JWT from JSON response and stores it in localStorage or sessionStorage.Protected Routes: Frontend HTTP client (e.g., Axios) intercepts outgoing requests, appending Authorization: Bearer <JWT> to the headers.Error Handling: If backend returns 401 Unauthorized (token expired), frontend instantly redirects to the Login screen and wipes local storage. If 403 Forbidden, frontend shows an "Access Denied" UI element.CORS: Backend must configure global CORS mapping to accept requests from the frontend origin (e.g., http://localhost:3000).32.
